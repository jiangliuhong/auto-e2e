# Auto-e2e Spec Coverage

交付 `.auto-e2e/coverage/review.yaml` 和 `report.md`，使项目方能核对功能范围、覆盖依据和待补场景。覆盖率只描述已盘点范围内的用例设计，不代表实际运行通过。

## 工作流程

1. 确定目标项目和用户指定范围。读取已有核对文件、项目约束、需求与相关实现。先使用可访问的本地资料；缺少资料时记录缺口，完成其余核对，不等待逐项确认。
2. 从需求、产品文档以及菜单、路由、接口和实现中盘点功能与原子验证点。区分需求来源和实现观察；代码中存在的行为不自动成为正确需求。不得用已有 Spec 作为唯一功能来源或统计分母。只有 Spec 的项目应标记功能范围未知，不报告全项目覆盖率。
3. 扫描 `.auto-e2e/specs/**/spec.json` 和旧版 `*.spec.json`；发现 bundle 后不再向内部递归寻找用例。尊重用户指定的其他路径。记录扫描范围、不可读或无效文件、重复 taskId，不能静默丢弃。聚焦模块时，报告必须写明模块分母。
4. 将验证点匹配到具体 Spec 结果断言，并记录源文件位置、匹配理由和遗漏。`requirementIds`、标题与 tags 只帮助寻找候选；进入页面、点击按钮或步骤成功本身不能证明业务结果。一个验证点可以关联多个断言或用例，统计时去重。
5. 写文件前读取 [references/review-format.md](references/review-format.md)，遵守状态、摘要、确认记录及统计约定。首次使用 [assets/review.yaml](assets/review.yaml) 初始化空清单，填入实际观察；已有文件按稳定 ID 合并，保留项目方确认和备注。
6. 生成覆盖矩阵、扫描限制、缺口、建议补充的场景和本次变更清单。给出候选覆盖率与已确认覆盖率；功能范围未确认时标为暂估。项目方可编辑 YAML 或在对话中确认，下一次执行根据反馈更新基线。

## 核对规则

- 读当前项目可用的 Spec 契约或随包文档。v2 使用 `taskId`、`requirementIds`、`steps`、`results`；结果依据指向 `RESULT-*`。没有可用校验器时，明确记录只做了结构和引用检查，不声称通过完整 Schema 校验。
- 旧版 `acceptanceCriteria` 使用零起始 JSON Pointer，例如 `/acceptanceCriteria/0`；`outputs` 使用 `/outputs/0`。只有可观察、可判断的预期行为才可作为覆盖依据。标注旧版来源，不假造 `RESULT-*`。
- 不新增 `coverage` 等字段到 Spec：当前 strict Schema 不接受这些字段。所有关联存放在独立的核对文件中。
- 不自动确认功能范围、覆盖或“不适用”。候选覆盖须检查前置条件、角色、输入、动作和断言是否共同覆盖验证点；只覆盖其中一部分时写明缺口。
- 多角色、异常、边界等验证点根据需求和实际风险提出；推断项注明依据，避免无限扩展范围。需求与实现冲突要单列，不能按实现改写需求来提高覆盖率。
- 默认只写核对材料与用例建议，不修改业务代码、Spec 或配置，不启动浏览器或 BetterWright。用户已明确授权补用例或执行验收时，再承接相应任务；静态结论与运行证据仍分开呈现。
- 项目方未回复不影响初次交付：报告保持待确认状态，并附少量具体核对问题。不得编造审阅人、确认时间或确认意见。

## 报告交付

`report.md` 至少包含：

- 范围、资料来源、扫描时间、未扫描或无法读取的区域，及“静态设计覆盖”的说明。
- 功能数、验证点数、候选覆盖数、已确认覆盖数、不适用数和需复核数；比例显示分子、分母，零分母为 `N/A`。
- 矩阵：功能 / 验证点 / 状态 / Spec 路径与断言 / 覆盖依据或缺口。附可定位的来源，方便项目方回看。
- 按业务风险排列的缺口及建议场景；不将建议伪装成已存在的用例。
- 相对已有基线的新增、失效、修改与需复核项；首次报告明确没有历史基线。
- 项目方核对说明：确认范围、检查断言、补充遗漏；可用自然语言反馈，或按格式编辑 `review.yaml`。保留报告对应的摘要，便于复现。

核对文件建议纳入项目版本管理。检查目标项目的忽略规则并说明文件是否被忽略；不要擅自修改忽略配置或提交文件。
